# Contributing to cpmesh

Thank you for your interest in contributing to cpmesh! This document provides guidelines and instructions for contributing.

## Before You Start

**Every contribution must start with a GitHub issue.** Whether it's a bug fix, new feature, or documentation improvement — open an issue first (or find an existing one) so the change can be discussed before any code is written. This helps avoid duplicated effort and ensures your contribution aligns with the project's direction.

1. Open or find a related [GitHub issue](https://github.com/cjs0h/cpmesh/issues)
2. Wait for maintainer approval before starting work on larger changes
3. Fork the repository and clone your fork locally
4. Create a new branch for your feature or bug fix

## Development Setup

### Server

```bash
# Requires Rust 1.94+, Node.js 22.12+ and a running PostgreSQL instance
cp .env.example .env
# Generate repo-local dev JWT keys
./scripts/generate-dev-jwt.sh
# Or on Windows PowerShell:
# pwsh ./scripts/generate-dev-jwt.ps1
#
# Then edit .env with the required secrets and database credentials
npm --prefix web ci
npm --prefix web run build  # RustEmbed requires web/dist, including for tests and Clippy
cargo build -p cpmesh-server
cargo run -p cpmesh-server
```

### Web Dashboard

```bash
# Requires Node.js 22.12+ (24 LTS recommended)
cd web
npm ci
npm run dev
```

### Desktop App

```bash
# Requires Node.js 22.17+ (24 LTS recommended)
cd desktop-tauri
npm ci
npx tauri dev
```

### JavaScript dependencies

`web`, `desktop-tauri` and `mcp/cpmesh-mcp` pin their dependencies in `package-lock.json`. Install them with `npm ci`,
and run it again after pulling a change to a lockfile. Their dev, build, check, typecheck and test scripts (and so
`tauri dev` and `tauri build`) first run `scripts/check-deps.mjs`, which stops with that instruction when
`node_modules` no longer matches the lockfile, instead of the build failing later with a "Cannot find module" error.
The `scripts/build-*` scripts run `npm ci` themselves in that case. Set `CPMESH_SKIP_DEPS_CHECK=1` to skip the check,
for example while trying out a dependency with `npm link`. The check's tests run with `node --test "scripts/*.test.mjs"`.

## Testing

All suites run in CI; please run the ones relevant to your change locally first.

### Rust

```bash
# On a clean checkout, build the embedded dashboard first:
npm --prefix web ci && npm --prefix web run build

# Server + shared proto crate: unit tests, router tests (no database needed) and wire-format tests
cargo test --workspace

# Desktop crate: crypto, key exchange, local history (SQLite), config and WebSocket client tests
cd desktop-tauri/src-tauri && cargo test
```

Desktop tests never touch the OS credential store (in test builds `SecureStore::new` stores secrets
in files) or a real relay: sign-in, key recovery and rotation flows run against stateful fake relays
built with `serve_with` in `src/api/client.rs`.

The server's PostgreSQL integration tests (`crates/cpmesh-server/tests/db.rs`) are skipped unless
`TEST_DATABASE_URL` is set. Each test migrates into its own throwaway schema, so any scratch
database works — for example with Docker:

```bash
docker run --rm -d --name cpmesh-test-pg -e POSTGRES_PASSWORD=pw -p 127.0.0.1:55432:5432 postgres:16-alpine
TEST_DATABASE_URL=postgres://postgres:pw@127.0.0.1:55432/postgres cargo test -p cpmesh-server --test db
docker rm -f cpmesh-test-pg
```

Lints are enforced with warnings denied, so also run:

```bash
cargo fmt --all -- --check && cargo clippy --workspace --all-targets -- -D warnings
cd desktop-tauri/src-tauri && cargo fmt --check && cargo clippy --all-targets -- -D warnings
```

### Frontends

Both frontends use [Vitest](https://vitest.dev/) for unit tests and `svelte-check` for type checking:

```bash
cd web && npm run check && npm test
cd desktop-tauri && npm run check && npm test
```

Tests live next to the code they cover (`*.test.ts`). Modules that use Svelte runes must be
tested from a `*.svelte.test.ts` file so the runes are compiled.

### MCP server

```bash
# The test toolchain needs Node.js 22.12+ (the published server itself runs on Node 18.19+)
cd mcp/cpmesh-mcp && npm ci && npm run typecheck && npm test && npm run build && node scripts/smoke.mjs
```

The crypto tests check the TypeScript port against golden vectors generated by the desktop
crate's own crypto code. After changing `desktop-tauri/src-tauri/src/crypto/`, regenerate them
and commit any difference (CI fails if they are stale):

```bash
cd mcp/cpmesh-mcp/vector-gen && cargo run --release > ../test/vectors.json
```

`vector-gen` compiles those crypto modules verbatim, so keep its Rust edition and crypto crate
versions in step with `desktop-tauri/src-tauri/Cargo.toml`.

The vectors also contain actual shared-Rust JSON and canonical membership signatures. The desktop
consumes `cpmesh-proto` directly; update these contracts and every client together.

For the same real-relay gate as MCP CI, build `web/dist`, the relay and the MCP executable, then provide
a **disposable loopback database whose name starts with `cpmesh_e2e`**:

```bash
cargo build --locked -p cpmesh-server
npm --prefix mcp/cpmesh-mcp run build
CPMESH_E2E_DATABASE_URL=postgres://postgres:pw@127.0.0.1:55432/cpmesh_e2e \
  node mcp/cpmesh-mcp/scripts/live-smoke.mjs
```

This creates a synthetic account with TOTP, uses a recovery code to sign in through the MCP protocol,
checks persistence/retry/restart, and probes two stalled 128 MiB installer downloads. It generates its own
keys and isolated profile, disables inherited auto-login credentials, and removes its processes and files.
The supplied database is not deleted automatically. Windows skips the Unix RSS probe.

### Dependency constraints

Compatible patch/minor updates are applied without changing the published MCP Node 18.19+ runtime target.
Its build uses patched esbuild directly rather than tsup's affected esbuild range; the Node 18/20 build and
stdio smoke matrix is retained. TypeScript 7, noble 2, Zod 4 and Node 26 typings are deliberately not forced
into the existing runtime/crypto contracts merely to make an outdated report empty.

Two upstream Linux GTK-chain notices remain in the desktop lockfile:

| Notice | Constraint |
|---|---|
| [GLib RUSTSEC-2024-0429](https://rustsec.org/advisories/RUSTSEC-2024-0429.html) | Tauri 2.12.4 still requires GTK 0.18 and GLib 0.18.5. The fix starts in GLib 0.20, which is not a compatible override. Linux reachability of `VariantStrIter` is unproven; a compatible upstream backport or GTK migration is still needed. |
| [proc-macro-error RUSTSEC-2024-0370](https://rustsec.org/advisories/RUSTSEC-2024-0370.html) | GTK/GLib macros still require the unmaintained 1.0.4 line. No patched release is listed. This is a maintenance notice, not a demonstrated runtime exploit. |

Do not suppress these notices or replace GTK/GLib with incompatible major versions. Recheck the upstream
graph on future Tauri updates and exercise Linux builds when a compatible fix becomes available.

### Web dashboard UI conventions

- The visual language is **minimal monochrome**: white surfaces, 1px `#e5e5e5` hairlines
  (`border border-border`), near-black text, Geist for UI text and Geist Mono for identifiers/code.
  Primary actions are solid black (`Button` default); the single coral accent (`text-accent`,
  `bg-accent`) is reserved for live indicators and small points of emphasis — never for large fills.
  Semantic states use the muted `success` / `warning` / `danger` tokens.
- Design tokens live in `web/src/app.css` (`@theme`): surfaces (`bg-bg`, `bg-bg-deep`, `bg-surface`,
  `bg-surface-2`, `bg-surface-3`), borders (`border-border`, `border-border-strong`), text (`text-fg`,
  `text-ink`, `text-muted`, `text-dim`) and the accent/semantic colours. Prefer these over raw hex values.
  Shadows are faint (`shadow-xs/sm/md/lg`) and used sparingly; there are no gradients or glows.
- Reusable primitives are in `web/src/components/ui/` (`Button`, `Card`, `Badge`, `Field`, `Select`, `Switch`,
  `Dialog`, `ConfirmAction`, `EmptyState`, `Alert`, `StatCard`, `Toaster`, …). Reach for these before
  hand-writing utility strings; page files should mostly be layout and data wiring. Use `.cell-grid`
  for feature/stat grids that should only show hairlines *between* cells, and `.tbl` for data tables.
- Motion is intentional and minimal: the only sustained animation is the `SyncDemo` product demo on the
  landing page (transform/opacity only, static frame under `prefers-reduced-motion`). Everything else is
  limited to ~150ms colour/border hover transitions. Do not add scroll-reveal, parallax, blur or
  background-plane animations; content must be visible immediately on load.
- Layout: the landing page uses the `.wrap` container (1200px, growing to 1360px/1520px on large
  monitors) with full-bleed hairline section dividers, and the app shell grows to 1600px, so wide screens
  do not feel boxed. Give every responsive grid an explicit `grid-cols-1` so single-column tracks cannot
  exceed the viewport.
- Mount-time data loading belongs in `onMount`, not `$effect`, so store reads inside the fetch
  (for example the clipboard `offset`) do not become reactive dependencies that re-trigger the load.
- User feedback goes through the `toast` store (`lib/stores/toast.svelte.ts`).

### Desktop app UI conventions

- The desktop app shares the web dashboard's brand: the same token names, Geist type, ink primary
  buttons and a single orange accent kept for live state (status dots, the mesh beam, the pending badge).
  Tokens live in `desktop-tauri/src/lib/app.css`; the dark theme only swaps their values under
  `:root.dark`, so prefer tokens (including the `*-soft` / `*-line` / `*-fg` semantic tints) over raw
  colours and `dark:` overrides. `lib/theme.svelte.ts` applies System/Light/Dark and syncs the native
  title bar.
- Primitives are in `desktop-tauri/src/lib/components/ui/` (`Button`, `Field`, `Switch`, `Segmented`,
  `Dialog`, `Alert`, `Badge`, `EmptyState`, `Skeleton`, `Fingerprint`, `Kbd`, `SettingsGroup`,
  `SettingRow`, …); screens are in `lib/components/` and `routes/`.
- Never use `window.confirm`/`alert` (webviews render them inconsistently): ask with
  `confirmAction()` from `lib/confirm.svelte.ts` and report outcomes with `toast` from
  `lib/toast.svelte.ts`.
- Fingerprints are always shown in full with the `Fingerprint` component (groups of four); never shorten them.
- Keep keyboard parity with desktop conventions: `⌘/Ctrl+1…4` switch sections, `⌘/Ctrl+,` opens
  Settings, `⌘/Ctrl+F` (or `/`) searches history. List in-app shortcuts under Settings → Keyboard
  shortcuts, and add them to `APP_SHORTCUTS` in `lib/shortcuts.ts` so the global shortcut can't take them.
- The global shortcut that shows cpmesh is saved as an accelerator (`global_hotkey` in `config.json`,
  `CmdOrCtrl+Shift+Space` by default, empty when turned off) and owned by `src-tauri/src/shortcut.rs`
  (the webview has no `global-shortcut:*` permissions):
  it registers the shortcut at startup and when Settings changes it (the new one before the old one is
  released, so a combination another app holds leaves the current one working), reports refusals to
  Settings and gives the tray menu its accelerator. Settings records new combinations with
  `ShortcutRecorder`; `lib/shortcuts.ts` turns key presses into accelerators and refuses ones that
  typing or other apps need. Signing out keeps it, like the other preferences of the computer.
- cpmesh is a background app: closing the window hides it (and its macOS Dock icon) while the tray /
  menu bar item in `src-tauri/src/tray.rs` keeps the status, recent clips and quick actions. "Open at
  login" launches it with `--background`, so it starts without a window. The tray and app menus open
  sections of the window by emitting `navigate` with a route.
- App and tray icons are generated from the SVGs in `src-tauri/icons/source/` (the website's mesh
  mark). After changing one, regenerate with `npx tauri icon` into a temporary directory and copy the
  files in: `app-icon.svg` for the PNG/ICO icons, `app-icon-macos.svg` for `icon.icns`, and
  `npx tauri icon --png 32,64` for the `tray*.svg` sources into `src-tauri/icons/tray/` (64px for the
  macOS template glyphs, 32px for the colour tray icons).

## Submitting Changes

1. Make sure your code compiles without warnings (`cargo check`, `cargo clippy`)
2. Add or update tests for your change and make sure the relevant suites pass
3. Commit your changes with a clear, descriptive commit message
4. Push to your fork and submit a pull request

## Pull Request Guidelines

- **Reference the GitHub issue** in your PR description (e.g., `Closes #42`)
- Keep PRs focused on a single change
- Describe what the PR does and why
- Make sure CI passes
- PRs without a linked issue may be closed

## Releasing

Maintainers publish releases with the [Release workflow](.github/workflows/release.yml). It builds every
app, attaches the installers to a GitHub Release, then registers that release on the website so the
Downloads section on cpmesh.com and the apps' update check offer the new version.

### Cutting a release

The version comes from the repository. Bump it with `scripts/release/set-version.mjs`, which writes it to
`tauri.conf.json`, `Cargo.toml`/`Cargo.lock` and `package.json`/`package-lock.json`, and get that commit onto the
branch you release from:

```bash
node scripts/release/set-version.mjs 0.5.0
git commit -am "Release 0.5.0"
```

Then tag that commit and push the tag (the subject of an annotated tag becomes the one-line note in the apps'
update banner):

```bash
git tag -a v0.5.0 -m "Faster sync and file previews"
git push origin v0.5.0
```

Or run **Actions → Release → Run workflow** on the bumped branch with the same version (`0.5.0`) and an optional
note; the branch is tagged `v0.5.0` when the release is published.

If the commit declares another version, the workflow stops before building anything: bump it, then re-create the tag
on the bump commit (`node scripts/release/set-version.mjs --check 0.5.0` runs the same check locally). This keeps
the repository at the latest released version, so an app built from it never reports an older version than the
published release, which its update check would otherwise offer as an update.

| Platform | Release asset |
| --- | --- |
| Windows x64 | `cpmesh-<version>-windows-amd64-setup.exe` (NSIS installer) |
| macOS (Apple silicon and Intel) | `cpmesh-<version>-macos-universal.dmg` |
| Linux x64 (built on Ubuntu 22.04) | `cpmesh-<version>-linux-amd64.deb`, `cpmesh-<version>-linux-amd64.AppImage` |
| Android (arm64, armv7, x86_64) | `cpmesh-<version>-android.apk` |

Each desktop installer is accompanied by `<installer>.sig`, the signature the in-app updater checks (see
[Signing updates](#signing-updates)).

The release stays a draft until every build succeeds; re-running failed jobs replaces the installers. Once it
is published, `scripts/release/publish-website.mjs` uses the server's admin API, authenticated with an API token,
to create a download link for each installer plus a current app release for each platform the update check reports
(`windows/amd64`, `darwin/arm64`, `darwin/amd64`, `linux/amd64`, `android/arm64`, `android/amd64`).
Re-publishing a version is safe, and the script refuses to replace a newer version unless run by hand with
`--force`. Use `--dry-run` to preview what a release JSON (from `gh release view <tag> --json tagName,url,isDraft,assets`)
would publish. The release scripts have tests: `node --test "scripts/release/*.test.mjs"`.

### Signing updates

The desktop apps install an update only when its signature verifies against the public key compiled into them
from `desktop-tauri/src-tauri/updater-key.pub`, the version it was signed for is newer than the running app, and it
was built for their platform. A compromised server therefore cannot push its own installer or an older release. The
Release workflow signs every installer with `scripts/release/sign-installers.sh` and uploads each signature next to
its installer as `<installer>.sig`.

To set up signing once:

1. Generate a key pair, protected by a strong password:

   ```bash
   cd desktop-tauri
   npx tauri signer generate -w ~/.tauri/cpmesh-updater.key
   ```

2. Add the contents of `~/.tauri/cpmesh-updater.key` as the `TAURI_SIGNING_PRIVATE_KEY` secret and its password as
   `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`.
3. Copy `~/.tauri/cpmesh-updater.key.pub` to `desktop-tauri/src-tauri/updater-key.pub` and commit it.

Keep the private key and its password backed up: apps only install updates signed with the key they were built
with, so without it users have to download new versions by hand. While `updater-key.pub` is empty, installers are
not signed and the apps do not install updates automatically. Once it is committed, a release fails if the private
key secret is missing, and every signature is checked against the public key before it is uploaded.

### Secrets and variables

| Name | Needed for | Purpose |
| --- | --- | --- |
| `TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | In-app updates | Signs the desktop installers (see [Signing updates](#signing-updates)) |
| `CPMESH_ADMIN_TOKEN` | Website update | API token with the `releases:write` scope, created by an owner or admin in the admin console (**API tokens**, `<server>/#/admin/tokens`); it expires after 90 days unless another period is chosen |
| `CPMESH_ADMIN_USERNAME`, `CPMESH_ADMIN_PASSWORD` | Optional | Admin sign-in instead of a token; only works on servers without two-factor authentication |
| `CPMESH_URL` (variable) | Optional | Server to update, `https://cpmesh.com` by default |
| `ANDROID_KEYSTORE_BASE64` | Android | The release keystore, base64 encoded |
| `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS` | Android | Keystore password and key alias |
| `ANDROID_KEY_PASSWORD` | Optional | Key password, when it differs from the keystore password |
| `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY` | Optional | Developer ID signing for macOS (base64 `.p12`) |
| `APPLE_ID`, `APPLE_PASSWORD`, `APPLE_TEAM_ID` | Optional | Notarization for macOS (app-specific password) |

Without the Android secrets the APK is skipped with a warning; without `CPMESH_ADMIN_TOKEN` (or the username and
password) the GitHub Release is still published but the website is left unchanged. Creating a token needs a recent
sign-in with your second factor; when the token expires or is revoked, the website step fails and explains how to
replace it. Android only installs an update signed with the
same key as the installed app, so keep the keystore and its password backed up. Without Apple credentials the
macOS app is ad-hoc signed and users allow it on first launch in **System Settings → Privacy & Security**;
the Windows installer is unsigned, so SmartScreen may warn as well.

## Reporting Bugs

Open an issue on GitHub with:

- A clear description of the bug
- Steps to reproduce
- Expected vs actual behavior
- Your environment (OS, Rust version, etc.)
